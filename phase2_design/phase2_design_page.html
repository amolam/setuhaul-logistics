The data model is proven on PostgreSQL 18 with the real snapshot, 3,240 contested holds, a truck-level guard, row-level security on all 16 facility- or driver-owned tables, least-privilege grants, and an enforced notification resend limit: 88 database checks pass, with the race tests running as the least-privilege agent role. India-only inference, the Aurora PostgreSQL 18 run, the golden dataset and measured cost are open Build gates.

Data model · 23 tables

Every claim on dock time is one row

CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE dock_occupancy (
  dock_id text, facility_id text, shipment_id text, vehicle_id text,  -- vehicle set by trigger
  during tstzrange CHECK (lower_inc(during) AND NOT upper_inc(during)), -- half-open [start, end)
  kind text CHECK (kind IN ('HOLD','APPOINTMENT','BLOCK','FIXED')),
  active boolean, expires_at timestamptz,
  CONSTRAINT ex_one_truck_per_dock EXCLUDE USING gist (dock_id WITH =, during WITH &&) WHERE (active),
  CONSTRAINT ex_one_dock_per_truck EXCLUDE USING gist
    (vehicle_id WITH =, during WITH &&, shipment_id WITH <>) WHERE (active AND vehicle_id IS NOT NULL)
);
GuardStops
Dock exclusionDouble booking, spill-over unloads, broken docks, overrunning trucks
Truck exclusionOne truck holding or booking two docks at once for different shipments
Compatibility triggerWrong facility, overweight, non-reefer, non-heavy, cancelled shipment
place_hold()Releases expired holds in the same transaction; per-dock lock prevents deadlocks
Unique ids, dedupe keys, idempotency recordsDuplicates beyond SQS's 5-minute window
FORCE row-level security on all 16 facility- or driver-owned tables, including shipments and the other mirror tablesCross-facility and cross-driver reads and writes; missing scope returns nothing and blocks writes; no bypass roles; a hidden shipment fails the write instead of skipping checks
Least-privilege grants: capacity changes only through owned, pinned-search-path functions; column-level writes per role; nothing for PUBLIC; no DELETEThe agent approving its own request, reading task tokens, clearing a human takeover or editing bookings directly
ex_one_dock_per_truck is not assignment validationIt stops one truck holding two overlapping docks. Whether the truck and driver are really assigned is TMS data, checked before options are offered and escalated as contradictory data
Notification state machineTwo notifications for one event and channel; unscheduled retries; ambiguous timeouts are marked UNKNOWN, never blindly re-sent
Append-only auditRewritten booking history
Tools & state machine

Ten tools, called by code, not chosen by the model

Tools (through AgentCore Gateway)

  • get_driver_context, record_driver_report, find_feasible_options
  • hold_option, submit_booking_request, release_hold, get_booking_status
  • request_location_pin, escalate_to_human, propose_facility_schedule
  • Identity from the session; every write idempotent; Policy and IAM still apply

Rules

  • A bare selection only moves the chat to SELECTED
  • Hold only after an explicit yes to the read-back
  • Only the warehouse or an auto-confirm rule confirms
  • Every time and dock in a reply must come from tool output
  • At most 3 clarifying questions, then a person

Agent design

The model reads and writes words; code does everything else

Pipeline

  • Ingest → Haiku extracts (forced tool, schema-validated) → Python validates, fuses the ETA, picks the operation → tools → Sonnet phrases (no tools) → grounding check → send
  • Status checks and confirmations use templates
  • On model failure: deterministic template replies with numbered options

Build-phase spikes

  • Strands' Bedrock provider (boto3 Converse) with both India profiles
  • Strict tool schema on Haiku 4.5 via Converse; fallback is Pydantic + one retry
  • Avoid the Anthropic SDK Bedrock client for Haiku 4.5: current releases send an API version Bedrock accepts only for Claude 4.7+
Data residency & guardrails

Driver data stays in India; masking is defence in depth

Residency decisions

  • Inference: India profile only (Mumbai ↔ Hyderabad); Global profiles denied in IAM. Designed; runtime proof pending in Build (B1–B4)
  • Phone numbers never reach a model; registrations and licences pseudonymised
  • Coordinates stay out of model context; only derived ETA and confidence
  • Evaluation data synthetic or sanitised; online evals on sanitised traces
  • All stateful data in ap-south-1

Protection matrix

  • Prompt injection: Guardrails on user input, and the model has no tools to misuse
  • PII: deterministic pre-mask + Guardrails sensitive-information filter
  • Bad output: strict schema + Pydantic; grounding check on replies
  • Tool results are data: driver text inside them is quoted, capped and never treated as instructions
  • "Cancel all appointments": no such operation exists for a driver

MVP acceptance gate · added at re-review

Done means a driver's delay ends in a confirmed reschedule

Definition of done (one trace end to end)

  • Driver signs in; the right driver and shipment are identified
  • Haiku extracts the ETA; Python validates and fuses it
  • Feasible options found; driver selects, then says yes to the read-back
  • Idempotent hold; booking request reaches the warehouse
  • Warehouse approves or rejects; driver gets the final outcome
  • Every step traced and audited

Failure scenarios that must pass

  • Duplicate driver message → one reply
  • Concurrent booking → one winner, losers get fresh options
  • Truck already assigned elsewhere → escalate; database rejects a forced booking
  • Expired hold → slot freed (tested)
  • LLM timeout → template reply
  • Warehouse timeout → no auto-approval; alternatives offered
  • Notification failure → retry, then fallback and alert
  • Wrong-facility access → 403 and 0 rows
