# Phase 1 · Frame — Solver Choice and OpenStreetMap Feasibility

Two technology questions: **which algorithm or solver should sequence trucks at a facility**, and **can OpenStreetMap (OSM) give us route times and maps cost-effectively**. Both were checked with evidence. The solver question was answered by a runnable spike on the snapshot (`solver_spike.py` → `solver_results.md`).

---

## Part A — Scheduling solver

### A1. What problem class is this?

One facility, one day: **parallel-machine scheduling with release times, machine eligibility, machine unavailability, fixed (in-progress) jobs, and a weighted waiting + lateness + stability objective.**

| Brief concept | Scheduling term |
|---|---|
| Truck / shipment | Job *j* |
| Dock door | Machine *m*, eligible only if `dock_compatible` |
| Latest ETA / gate-in | Release time `r_j` |
| Unload + changeover | Processing time `p_j` |
| Appointment | Due time `d_j` |
| Truck in dock | Fixed job (immovable) |
| Breakdown / maintenance | Machine unavailability window |
| Priority | Weight `w_j` |

**Size:** about 40–60 jobs × 5–6 docks per facility per day. Each event re-solves only the remaining horizon, usually fewer than 25 jobs. This is **small**. Any exact method solves it in seconds, so the choice should be driven by explainability, operability and fit with the stack, not raw power.

### A2. Candidates

| Option | What it is | Fit for SetuHaul | Verdict |
|---|---|---|---|
| **Dispatch rules** (FCFS, priority-weighted, EDD, ATC) | Sort jobs, then greedily take the earliest compatible dock | Instant and fully explainable. Can be myopic (see spike) | **Keep** as the real-time option generator and as the baseline |
| **Google OR-Tools CP-SAT** (v9.15, Python, Apache-2.0) | Constraint programming with interval variables, `NoOverlap`, optional intervals | Native Python. Models eligibility, unavailability, fixed tasks and the stability penalty directly. Optimal on the snapshot in 1.4 s | **Recommended** for facility re-sequencing proposals |
| MILP (HiGHS via PuLP / Pyomo) | Time-indexed or big-M formulation | Works, but scheduling disjunctions are clumsier and slower than CP-SAT | Not chosen |
| **OptaPlanner** (Apache KIE) / **Timefold Solver** (its fork) | Java / Kotlin metaheuristic constraint solver (local search, tabu, late acceptance) | Strong for large VRP and rostering. Here it adds a **JVM service** to a Python stack. Timefold's **official Python solver was discontinued**: the repo was archived in Oct 2025 and Timefold now focuses on Java and Kotlin. A community fork (SolverForge) exists but is unofficial. Its metaheuristic advantage only matters at hundreds or thousands of jobs, and it gives no optimality proof | **Not chosen for v1.** Revisit if we move to network-level VRP or large rostering |
| Commercial (Gurobi, Hexaly) | Licensed solvers | Unnecessary at this size, and licence cost | No |
| Google Route Optimization API | Vehicle routing as a service | Solves routing, not dock sequencing | No |

### A3. Spike result on the Jaipur snapshot (09:56, 16 movable trucks)

Generated by `python scripts/frame/solver_spike.py`. Objective: Σ w·wait + 2·Σ w·lateness vs promise + 30·changed promises + 2000·w·unscheduled. Weights: CRITICAL 8, HIGH 4, NORMAL 2, LOW 1.

| Method | Weighted wait | Total wait (min) | Max wait | Missed promises | Changed promises | Escalated | Runtime |
|---|---:|---:|---:|---:|---:|---:|---|
| FCFS by ready time | 1134 | 320 | 61 | 8 | 9 | 1 | < 1 ms |
| Priority-weighted dispatch | 1177 | 718 | 180 | 9 | 9 | 1 | < 1 ms |
| Keep promises first (EDD) | 1296 | 418 | 100 | 9 | 9 | 1 | < 1 ms |
| **CP-SAT** (optimal) | **768** | 381 | 139 | **7** | **7** | 1 | 1.4 s |

**What the spike shows**

1. **CP-SAT cuts weighted waiting by 32 % against FCFS** and breaks the fewest promises. That supports using a solver for the facility view.
2. **The obvious priority rule is worse than FCFS.** Moving every CRITICAL truck first leaves docks idle while high-priority trucks are still on the road (max wait 180 min). This is the trap the brief warns about: an early truck should not automatically win, and a high-priority truck should not automatically block.
3. **Fairness needs an explicit constraint.** CP-SAT made SHP1004 (NORMAL, in the yard since 09:25) wait 139 min to serve higher weights. Design must add a hard `max_yard_wait_min` (e.g. 90) or an ageing term that raises a job's weight the longer it waits. This is a business choice (decision 7), now backed by evidence.
4. **Escalation is identical across all methods.** SHP1015 (reefer) cannot be scheduled by any method, so solver choice never replaces the no-slot escalation path.
5. Eight to nine "missed promises" are already baked into the snapshot (09:00–11:00 slots the trucks cannot meet). The measure that matters is the delta between methods.

### A4. Recommendation

| Use | Method | Latency budget | Notes |
|---|---|---|---|
| **Per-driver options** (agent tool `find_feasible_options`) | `is_feasible()` plus the transparent ranking (§3 of `02_variables.md`) | < 300 ms | Never waits for a solver |
| **Facility re-sequence proposal** (`propose_facility_schedule`): on an ETA change, gate-in, dock event or cancellation | **CP-SAT** with a 2–5 s time limit and `num_workers` = vCPUs. Hard constraints: compatibility, no overlap, release, fixed tasks, unavailability, last-start rule, driver latest-finish, `max_yard_wait_min` | ≤ 5 s | If the solver times out, return the best of FCFS, EDD and priority dispatch. The tool always returns |
| **Applying** a proposal | Booking service, move by move, each re-checked with `is_feasible()` | — | Unconfirmed and AT_RISK moves can apply automatically. Moving another driver's **on-time confirmed** promise needs planner approval |

**Deployment:** Python Lambda as a **container image**, because the OR-Tools wheel plus dependencies is tens of MB. Use ≥ 3,538 MB memory so Lambda allocates ≥ 2 vCPUs for parallel CP-SAT workers. Called through AgentCore Gateway like every other tool. Inputs are structured state only, never chat text.

**Explainability:** every proposal carries per-truck reasons ("D2 at 11:35 because D1 / D3 are below 21 t and D4 is occupied until 12:26"), produced from the constraint data, not by the LLM.

## Part B — OpenStreetMap (OSM) feasibility

### B1. What we would use maps for

| Need | Frequency | Needed in v1? |
|---|---|---|
| Drive time from a known point (FASTag plaza, location pin, SIM ping) to the facility (signal S8) | Event-driven, tens per day | Yes |
| Facility, origin and toll-plaza coordinates | Static, a few hundred points | Yes, as a static table |
| Truck-legal routing (weight, height, city no-entry windows) | Same calls as drive time | Desirable |
| Live traffic | — | Nice to have |
| Map display in the ops console | Ops users only | Optional |

### B2. Options

| Option | Feasible? | Why |
|---|---|---|
| **Public OSM services**: `tile.openstreetmap.org`, `nominatim.openstreetmap.org`, the OSRM demo server | ❌ **Not for production** | Donated capacity. Nominatim allows at most 1 request/s per application, summed over all users, and access can be withdrawn. The OSRM demo server forbids heavy use and anything with SLA needs, and can be withdrawn without reason. The tile policy restricts heavy use |
| **Self-hosted OSM routing engine** on an India extract: **Valhalla**, OSRM or GraphHopper | ✅ **Feasible** | ODbL data, open-source engines. **Valhalla** fits best: its `truck` costing honours weight, height, length, axle load and hazmat at request time, with no graph rebuild. OSRM is fastest but needs a rebuild per vehicle profile |
| **Amazon Location Service** (commercial map data, traffic-aware routes, per-request pricing) | ⚠️ **Feasible if available in ap-south-1** (not yet verified) | Managed, no servers, traffic-aware. India data quality and region availability must be checked |
| Commercial India APIs (e.g. Mappls / MapmyIndia, Google Routes) | ✅ | Strong India coverage, per-request cost. A vendor decision |

### B3. Caveats for OSM in India

- **No live traffic.** OSM ETAs use free-flow speed profiles. Calibrate with SetuHaul's own history (signal S9: per-lane slip from `eta_updates` vs gate-in).
- **Truck restrictions are thinly tagged.** City no-entry windows for heavy vehicles (common in Indian cities) are often missing. Maintain a small restriction overlay for the six facility cities and their approach roads.
- **Highway coverage** on the NH corridors SetuHaul uses is generally good. This needs a spot check against known lane times before go-live.
- **Licence.** ODbL requires attribution ("© OpenStreetMap contributors"). Share-alike applies to publicly distributed derived databases, not to internal routing results. Confirm with legal.

### B4. Recommendation (cost-optimal)

| Stage | Approach | Runtime cost |
|---|---|---|
| **v1 (now)** | **No runtime routing service.** Precompute, offline, a **drive-time matrix** from every toll plaza on SetuHaul's lanes, and from a grid of common pin locations, to each of the 6 facilities using self-hosted Valhalla (`truck` costing) on a build machine. Store it as a table. FASTag plaza → facility ETA becomes a lookup | ≈ 0 |
| **v1.5** | For location pins and SIM pings that fall off the matrix, interpolate from the nearest matrix point, flagged `uncertainty_min` +15 | ≈ 0 |
| **v2** (if pin or SIM volume grows, or accuracy is short) | Valhalla on ECS Fargate in ap-south-1, behind the internal ALB, called by `fuse_eta()`. **Or** Amazon Location Service if it is verified in region and its India data beats OSM on our lanes | Small fixed container cost, or per-request |
| Console maps | Self-hosted vector tiles (PMTiles on S3 + CloudFront) **or** Amazon Location maps. Never the public OSM tile server | Small |

**Never** call the public OSM, Nominatim or OSRM servers from the product.
