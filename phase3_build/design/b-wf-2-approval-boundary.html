Warehouse approval boundary

Architecture approved. Revision 2 adds your decisions and clarifications A–E. For review, not implemented

The agent can only ask. A request becomes CONFIRMED only when an authenticated warehouse person decides inside a database function. That function enforces every booking and capacity rule itself, before one deadline shared by the request and its claim on the slot. Every other outcome is final and recorded. Step Functions only waits, and the driver's notification never depends on it. Policy confirmation is a separate path, never recorded as a human approval, and every rule ships switched off. The booking switch stays off.

Your decisions

Q1 · Policy rulesRule table ships with every rule set to NEEDS_PLANNER. A policy confirmation records basis POLICY with its rule id, never APPROVED, never a person, never the AI.
Q2 · RolesMapping accepted. operations is now defined, and every permission is facility-scoped from the verified session.
Q3 · Pauses and holdsAn automation pause stops only the agent. A new operational or safety hold blocks approvals and new requests.
Q4 · WithdrawalStaff only, with a reason code. WITHDRAWN (with DRIVER_REQUESTED as one reason code) is kept separate from SUPERSEDED (replaced by another booking).

Already bound to the conversation, the option, the selection and the exact message; any later driver message voids it; expires in 10 minutes. Revision 2 adds snapshot columns, compares them again at submission, and lets each YES be used once.

After submission, a new driver message does not silently cancel the request. A "cancel" goes to a coordinator, who withdraws it with reason DRIVER_REQUESTED.

B · The database decides feasibility clarification

The application check is advisory, for an early, clear message. Every critical rule is enforced again inside the function, atomically, under row locks.

  • One truck per dock at a time, and one vehicle per time window: existing exclusion constraints.
  • One current booking per shipment: existing unique index.
  • The claim is active and matches the dock and slot exactly: checked in the function and by a commit-time trigger.
  • The dock is active, compatible and not blocked; the slot is inside operating hours unless its kind allows otherwise.
  • The slot starts at least the lead time from now; the shipment is not cancelled and not already in the dock.
  • No operational hold. The decider's role and facility are taken from the session.

D + E · One deadline; nothing left unapprovable clarification

deadline = least( now() + warehouse TTL for the shift,
                  slot start − confirmation lead time,
                  the hold's own expiry )            ← computed once, at submission
  • The hold row becomes the request's claim and carries the same deadline. Expiry releases both in one transaction.
  • A deferred trigger refuses any commit that leaves an OPEN request with an inactive claim, or a claim that no longer matches.
  • Because the deadline is at or before the slot start minus the lead time, a request can never be OPEN once its slot is too late. Approval is refused after the deadline even before the sweep runs.
  • When capacity is lost, the request is invalidated in the same transaction: a dock block records CAPACITY_LOST, dock deactivation DOCK_UNAVAILABLE, a shipment change SHIPMENT_CHANGED, changed hours OUTSIDE_HOURS.
  • An operational hold blocks approval but does not invalidate; the request expires normally if the hold lasts past the deadline.

C · Durable events; Step Functions only waits clarification

Every final transition writes an ApprovalDecided outbox event (approval, appointment, outcome, reason, decider type, time), the existing booking event and an audit row, all in the same transaction. Driver notification (B-WF-3) reads the outbox, so it works with the workflow stopped.
